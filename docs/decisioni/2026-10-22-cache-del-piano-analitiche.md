# Analytics plan cached on Redis for the sidebar and the Goals view (2026-10-22)

Production check on 2026-10-22 after "the app feels slow": the node was idle (10% CPU), but `goals.list` had a p50 of 900 ms, `net_worth.snapshots` and `sidebar.fire` peaked near 2 s, and the event loop of a pod stalled up to 0.8 s, so even trivial requests on the same pod (`budgets.list`, one select) reached 750 ms at p95. Panoramica asked for the full Analytics snapshot twice at once (`/api/sidebar/fire` and `/api/goals`), on pods limited to half a core.

Decision: both now read `loadAnalyticsDigest` (`lib/analitiche/digest.ts`), a JSON-safe subset of the snapshot cached on Redis (`analytics:digest:<userId>`, 30-minute TTL) and used only while its input fingerprint (the cash and investment history markers, an md5 of the small per-user tables, currency, country, day) matches. Parallel calls in one pod share one computation. Same pattern as the net worth history fingerprints; no migration. The goals rows stay uncached. Metric `buddybudget_analytics_digest_total{outcome=hit|miss|shared}` and `buddybudget_analytics_digest_compute_duration_seconds`; living doc §4.17 of `docs/architecture/analytics-and-goals.md`.

Deferred: `investments.performance` (3.5 s, used only by the native app API) and `net_worth.snapshots` spikes, to profile on real-sized data; raising the app CPU limit from 500m and scraping cAdvisor container metrics (infra repo). Found on the way: the local `.env.local` points at the production database, and `pnpm test` loads it (`vitest.setup.ts`), so local integration tests would write to production.
