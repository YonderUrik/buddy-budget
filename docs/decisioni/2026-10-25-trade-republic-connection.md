# Direct Trade Republic cash connection

Branch: `codex/trade-republic-import`, based on current `main`.

Trade Republic is available under New account → Connect your bank, separately from the GoCardless capacity limit. The clearly labelled BuddyBudget form sends phone/PIN once to TR's v2 web login, then polls for app approval or verifies an authenticator code. Credentials and codes are not stored. Pending session cookies are AES-GCM encrypted in user-scoped Redis keys with a fixed three-minute TTL. Completed sessions are encrypted in `trade_republic_connections` (migration 0050); encryption is mandatory even when other fields may be stored in plaintext on a self-hosted install.

Data comes directly from `/api/v2/auth/account` and cookie-authenticated WebSocket subscriptions to `cash` and paginated `timelineTransactions`. There is no CSV export request, file upload, token-pasting screen or browser-session interception. The current private web protocol authenticates with session cookies; it does not document a separate bearer-JWT exchange. Sources inspected: https://github.com/pytr-org/pytr/blob/master/pytr/api.py and https://github.com/cdamken/tr-api/blob/main/src/tr_api/protocol.py .

Initial import and manual refresh use the existing global background sync jobs. The cash balance and complete recognized cash history are saved atomically; provider IDs prevent duplicate movements and existing notes/categories survive refresh. Reconnection verifies account identity and reuses the existing account. Expired sessions are cleared and the account offers a new sign-in. Disconnecting deletes the saved session through the account FK cascade.

Scope: EUR cash accounts with EUR as the user's main currency. Security trades and savings-plan executions are excluded from spending; direct investment-position/history ingestion and scheduled unattended refresh are deferred. Dividend cash is imported. Unknown monetary events, incomplete pagination, inconsistent duplicate IDs and unsupported currencies block the entire refresh. Prior TR file imports are refused to prevent double counting between two sources whose identifiers have not been verified to match. Those constraints are explicit in the form or returned error; no data is silently discarded.

Verification: synthetic HTTP/socket tests, authenticated-route tests, encryption tests and real local Postgres tests for reimport, ownership, rollback, reconnection and account deletion. Real TR authentication remains to be tested by the account holder on staging. The private protocol can change or reject server-side sign-in; there is no WAF bypass. Landing catalog, security and privacy copy explain direct credential handling separately from PSD2 consent. No promise that the saved TR session itself is technically read-only.

Signals: `trade_republic.login.started|completed|failed`, `trade_republic.sync.completed|failed`; `buddybudget_trade_republic_requests_total{action,outcome}` and `buddybudget_trade_republic_request_seconds`; Umami `trade_republic_login_started` / `trade_republic_connected` plus existing manual-sync events. Logs contain only counts and categorical reasons, never provider response bodies or credentials. Before production, add the new counter/histogram to the infrastructure dashboard and validate live TR behavior; staging deployment does not deploy the landing or production infrastructure.
