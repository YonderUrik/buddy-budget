# 2026-11-01 — Investment history fingerprint sees corrected closes and FX rates

Found reviewing the investment history (P0, data correctness): `instrument_prices` and `fx_rates` carried only `created_at`, and the upserts that store a close or a rate (`savePrices` with `overwrite: true`, `saveFxRates` in `lib/market-data/store.ts`) replaced value and source without touching it. The investment-history fingerprint (`investmentInputsFingerprint` in `lib/net-worth/investments.ts`) was built with `count(*) + max(created_at)` on both tables, so correcting an already-stored close or rate left the fingerprint unchanged: `refreshDerivedInvestmentHistory` returned 0 and the past `investimenti` rows kept the old value. The Investimenti screen read the fresh price while the net worth chart stayed stale until the next day (or another change) forced a recompute.

Fix: both tables get `updated_at` (migration `0053_market_data_updated_at`), refreshed on every upsert, and the fingerprint uses it instead of `created_at`. Existing rows take `now()` from the column default, so the first refresh after the deploy recomputes them once. This is the state the living doc already described ("count and latest change").

Acceptance (met): after a retroactive correction of a close or a rate, the first history read returns the corrected value, without waiting for the nightly cron or another change. Tests in `lib/net-worth/investments.test.ts` go through the real store, not a raw update: correcting a stored close recomputes the history; correcting a historical rate recomputes the value in the user's currency; an upsert with the same value does not recompute.

Still open (deferred, structural): `count + max(updated_at)` is not an absolute guarantee (coincident timestamps, compensating delete + insert). A monotone per-instrument/per-currency revision counter, bumped in the same transaction as the write and represented deterministically in the fingerprint, is the robust version; it is a separate change, not needed for this fix.
