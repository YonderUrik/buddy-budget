# 0002 — Thin clients: computed views live on the server

Date: 2026-10-18 · Status: proposed

## Context
The web computes most figures in the browser from raw rows: Liquidità KPIs, the whole
investments engine (positions, returns, Italian taxes), pension figures, Analitiche
(see `domain/README.md`, `api/gaps.md`). Porting all of it to Swift *and* Kotlin would mean
maintaining three copies of the financial engine.

## Decision
- Add **view endpoints** to the web backend that run the existing TypeScript functions
  and return display-ready data (`GET /api/overview`, `/api/liquidity/month`,
  `/api/investments/view`, `/api/pension/view`, `/api/analytics/base`, …; list in `api/gaps.md`).
  The web can migrate to them too, so there is still one engine.
- Port to Swift/Kotlin **only** what must react instantly to a slider or a form field
  (debt simulators, pension exit-tax timeline, FIRE "e se…", Monte Carlo, goal wizard,
  period helpers, "Dividi", formatting). Every ported function is pinned by the golden
  vectors in `domain/vectors/`, generated by running the web code.
- Anything heavy but not interactive (e.g. sale-tax simulation) is a debounced server call.

## Consequences
- Mobile work depends on backend PRs in `buddy-budget`; the roadmap sequences them first.
- When a ported formula changes on the web, its vectors are regenerated
  (`domain/tools/`) and both apps' tests fail until updated — that is the parity guard.
